# Подписочный сервис • Данные к итоговому проекту

Это исходные данные для темы 3. За январь, февраль и март 2026 года сервис выставлял счета в EUR и USD. Клиенты могли иметь несколько подписок. Вы построите две витрины из задания: состояние подписок на дату и расчёты по счетам на дату. Все идентификаторы и операции синтетические.

## С чего начать

1. Распакуйте весь архив. Из папки с README запустите в отдельном терминале: `python3 api.py` (Windows: `py api.py`). Нужен Python 3.8 или новее, дополнительные пакеты для сервера не требуются. Оставьте терминал открытым.
2. Откройте в браузере http://127.0.0.1:8765/payments?batch=01_full&limit=5 . Первые пять записей и ссылка next означают, что источник доступен. По умолчанию сервис слушает только на этом компьютере. Для учебного Airflow запускайте сервис в среде, из которой worker может обратиться к нему; внутри отдельного контейнера localhost относится к самому контейнеру.
3. Возьмите CSV и subscriptions.json из data/01_full, а платежи той же поставки получите через HTTP. Сверьте полученное с manifest.json. В каждой папке api_source.json служит хранилищем учебного сервера, а не файловым входом загрузчика.
4. После полной загрузки обработайте 02_delta и 03_delta по порядку. Для независимой сверки загрузите 04_full_reference в отдельную пустую схему. Это снимок того же состояния источника после обеих дельт, а не четвёртая порция изменений.
5. Для пустого периода используйте 05_empty_delta. Папки test_* — независимые альтернативы после этого периода. Перед каждым таким испытанием восстанавливайте одинаковое начальное состояние. Не объединяйте эти папки в одну последовательность.

Все файлы в UTF-8, CSV с заголовком и разделителем-запятой. Десятичный разделитель — точка. Денежные значения сравниваются до цента отдельно по валютам. Пустое поле означает отсутствие значения.

## Договор источников

| Источник | Ключ и содержание |
|---|---|
| customers.csv | customer_id — клиент; segment и acquisition_channel — сегмент и канал привлечения. Сегмент может исправляться без изменения бизнес-ключа (кандидат на Type 1). |
| plans.csv | catalog_event_id — запись каталога. plan_id — устойчивый идентификатор тарифа в своей валюте. tier — уровень, currency — валюта, monthly_price — цена начиная с effective_from включительно и до следующего изменения этого plan_id исключительно. До первой даты такая версия не действует. Новая цена — новое событие каталога, а не новая подписка. |
| subscriptions.json | subscriptions[] содержит subscription_id, customer_id и массив events[]. Одна запись events[] — событие event_id. Состояние state и назначенный plan_id действуют с effective_at. active — действует, paused — приостановлена, cancelled — прекращена. В дельте приходят только изменившиеся события; отсутствие предыдущего события не отменяет его. |
| invoices.csv | invoice_id — счёт одной subscription_id; issued_at — момент начисления, due_date — последний день оплаты включительно. amount и currency — выставленная сумма и валюта. Счёт связан с тарифом через подписку на момент выставления. |
| GET /payments | payment_id — попытка оплаты одного invoice_id; paid_at — время операции, status — succeeded или failed. В расчётах учитываются успешные операции; failed не уменьшает долг. Несколько успешных оплат одного счёта допустимы. |
| refunds.csv | refund_id — отдельный возврат; payment_id — исходная оплата. refunded_at — момент возврата. Успешный возврат сторнирует часть ранее зачтённой оплаты: в этой модели начисление остаётся прежним. Возврат не меняет состояние подписки автоматически. |

version — целочисленная версия записи внутри её устойчивого ключа. updated_at — время регистрации версии у источника, используется для отбора изменений. Оно может отличаться от времени события. Даты-время выражены в UTC; отчётные сутки также в UTC. due_date относится к календарю UTC. Для остатков на конец дня учитывайте события до начала следующих суток. Исторические исправления трактуйте как пересчёт по последнему известному состоянию данных. Подписка, приостановленная или отменённая в середине месяца, не аннулирует уже выставленный счёт; автоматических кредит-нот в наборе нет.

В полной поставке доступна последняя известная версия каждого ключа, включая все отдельные события истории подписок и каталога. В дельте присутствуют только зарегистрированные изменения. manifest.json указывает границы по updated_at: from_inclusive включительно, until_exclusive исключительно. null у нижней границы означает всю доступную историю. complete=false означает, что полнота не подтверждена. counts — число записей в поставке до преобразований; events считаются по элементам вложенных массивов. amounts_by_currency — суммы предъявленных счетов и успешных платежей/возвратов именно в данной поставке, не величина изменения долга. Исправленная версия передаёт целую запись, а не разницу сумм.

## HTTP API

GET /payments?batch=02_delta&page=1&limit=10 . Параметр batch выбирает неизменяемую поставку из data; для инкрементального чтения выбирайте поставку по границам в её manifest. API не фильтрует отдельно по paid_at. page начинается с 1, limit от 1 до 50. Ответ: items (массив), total (число во всей поставке), next (путь следующей страницы от корня сервера или null в конце). Пустая поставка возвращает 200, пустой items, total=0 и next=null. Авторизация не нужна.

Для воспроизводимых тестов используйте 01_full и limit=5:
- fault=once&trial=A: первая попытка получить страницу 2 возвращает 503 с Retry-After; следующий запрос этой страницы успешен. Новый trial запускает новый эксперимент.
- fault=always: страница 2 недоступна при каждой попытке.
- fault=broken_json: статус 200, но тело нельзя разобрать как JSON.
Ошибочные параметры страницы или неизвестный batch возвращают 400. Остановить сервер: Ctrl+C.

## Контрольные случаи

- test_warning: пропущен необязательный канал привлечения. test_critical: платёж с нарушением ссылочной целостности и недопустимой суммой. test_incomplete: нет подтверждения полноты. test_stale_version и test_version_conflict: старая версия и противоречие одной версии ключа.
- 05_empty_delta — подтверждённое отсутствие изменений, а не удаление имеющихся данных.
- Для проверки истории проследите, например, S0006 (смена тарифа), S0010 (пауза и возобновление), S0008 (отмена).
- Для проверки расчётов сравните счёт I0002-01 до и после дельты: вторая январская оплата зарегистрирована в феврале. У P0001-01-1 исправление суммы поступает в марте. Возврат по I0015-01 проходит в следующем месяце.
- Временные сбои API имитирует сервер. Сбой после фиксации staging, откат публикации, повтор задач и ошибку привязки проверки к load_id моделируйте в собственном тестовом запуске. Результаты витрин и готовый DAG в набор не входят.

Данные уже подготовлены. Для воспроизведения источника можно выполнить python3 generate.py в этой папке: он заново запишет поставки в data. Работа загрузчика не должна изменять исходные файлы.
